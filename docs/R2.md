# R2: contain and record `symbia_exec`, seal on exit

A benchmark on 6 Oct showed three problems. The path policy guards the file tools, but `symbia_exec` checks only its `cwd`, so `cat ~/.ssh/id_ed25519` through exec works. Exec records keep the argument digest but not the command, so an auditor holding only the ledger cannot tell what ran. And none of six benchmark sessions was sealed, because nothing seals when the client goes away. Read CLAUDE.md, then make these changes. Keep every existing test passing.

## 1. Run exec inside the macOS sandbox

On macOS, run the command as `/usr/bin/sandbox-exec -p <profile> /bin/zsh -lc <command>`. The profile is generated per call from the loaded `Policy`:

```
(version 1)
(allow default)
(deny file-read* file-write* (subpath "<each deny-list path>"))
```

- Use every deny-list path (the five `DENY_IN_HOME` entries under the policy's user home, plus `$SYMBIA_HOME/keys`), each both as spelled and as its realpath when that differs. Quote paths for the SBPL string literal (escape `\` and `"`).
- Also deny `file-write*` on `$SYMBIA_HOME` (it is read-only to the tools already; exec must not get around that).
- Network: a new optional config key in `$SYMBIA_HOME/config.json`, `"exec_network": "allow" | "deny"`, default `"allow"`. With `"deny"`, add `(deny network-outbound)` and `(allow network-outbound (remote unix-socket))`, so local sockets keep working and nothing reaches an IP address, loopback included.
- Process group handling, timeout kill and output capture stay as they are. Kill the sandbox-exec process group the same way.
- On Linux there is no sandbox yet: run as today and set `sandbox: "none"` in the facts. On macOS set `sandbox: "seatbelt"`.
- If `/usr/bin/sandbox-exec` is missing on macOS, refuse the call with a clear error rather than running unsandboxed.

## 2. Record what ran

The `tool_call` record body for `symbia_exec` gains:

- `command`: the full command text as given.
- `sandbox`: `"seatbelt"` or `"none"`.
- `network`: `"allow"` or `"deny"`.

Document in the `symbia_exec` tool description, in one short sentence, that commands run sandboxed: deny-list paths and the data directory are off limits, and network may be off.

## 3. Seal on exit

When the stdio MCP transport closes (client exit or EOF), seal the session before the process exits if any record was written after the last seal. Same for `symbia serve` on shutdown (SIGINT/SIGTERM). Never seal an empty session. A failure to seal on exit goes to stderr; the process still exits.

## 4. Tests

- Exec `cat <home>/.ssh/id_test` with a temp user home that has the file: nonzero exit, and the file's content is not in stdout or in the evidence file.
- Same for a file under `$SYMBIA_HOME/keys`, and for `echo x > $SYMBIA_HOME/x` (write refused).
- Reading and writing a file inside a root still works; `cargo --version` still runs.
- With `exec_network: "deny"`, a test opens a TCP listener on 127.0.0.1 and `curl -s -m 3 http://127.0.0.1:<port>/` through exec fails and the listener sees no connection. With the default, it succeeds.
- The exec record contains `command`, `sandbox` and `network`.
- A path containing `"` and a space on the deny list does not break the profile.
- Seal on exit: spawn the binary over stdio with a temp `SYMBIA_HOME`, write one record, close stdin, wait for exit; `seals/` holds one seal and `symbia verify` accepts it. A session with no records leaves no seal.

Mark sandbox tests `#[cfg(target_os = "macos")]`.
