# R10: the audit path

The first pillar is an independent record that someone else can check. Four gaps remain:

- An auditor can't read a seal over MCP.
- Seals never move into a long-lived ledger.
- Checkpoint seals pile up: one every 50 records and one at every exit.
- Nothing outside the data folder remembers what was sealed, so deleting or rolling back a session goes unnoticed.

Read CLAUDE.md, docs/R8-REPORT.md, docs/R9-REPORT.md and the "Sessions, seals and promotion" section of the v2 brief first. Keep every existing test passing.

## 1. Why a seal was made

The sidecar gains `reason`: `explicit` (`symbia_seal`), `prediction` (sealed at once after a prediction), `checkpoint` (every 50 records), `exit` (seal on exit) or `ledger` (a seal of the ledger file). It is left out when absent, so older sidecars still parse. The signature and the file hash are unchanged.

## 2. Pruning superseded copies

After a full seal of a session verifies, Symbia deletes the older full seals of that session whose reason is `checkpoint` or `exit` (file and sidecar). Explicit and prediction seals are kept, as are thread seals and seals with no reason (older builds). A newer seal holds every record an older one did, so nothing in the chain is lost. When a witness is configured (section 3), each pruned seal's head and signature also stay in the witness file.

## 3. The witness

- Config `witness`: a folder outside `$SYMBIA_HOME` (a leading `~` is expanded). Config load fails on a folder inside the data directory.
- **What is written:** after every seal (full, thread or ledger), Symbia appends one line to `<folder>/witness.jsonl`: `{session, chain_seq, chain_head, file_sha256, public_key, signature, at_ms, reason, thread?}`. It creates the folder and file if missing. A failed append goes to stderr and never fails the seal.
- **Where to keep it:** the folder can sit somewhere that leaves the machine (iCloud Drive, a git repo you push) so the witness outlives the disk.
- **Checking a full seal against a witness:**
  - For every line of the same session with `chain_seq` up to the file's: the file's chain hash at that seq must equal the line's head (genesis at seq 0). Otherwise: `witness mismatch at seq <n>`, a failure.
  - Lines of that session with a higher seq: the file is behind what the witness saw, which means a rollback if this is offered as the latest. Report `witness: behind (seen seq <n>)`. This is a warning, not a failure.
  - No lines: `witness: not witnessed`.
  - Otherwise: `witness: ok (<k> entries)`.
- **Thread seals** are checked the same way. Their chain rows and heads are the full chain's.
- **The CLI:** `symbia verify <file> --witness <path>` adds the witness line to its output, and exits 1 on a mismatch.

## 4. `symbia_open`

New tool. It reads a sealed copy, without writing to it.

- **Arguments:** `path`, optional `id`, and `limit` (default 20, at most 50).
- **Allowed paths:** inside `$SYMBIA_HOME/seals` or `$SYMBIA_HOME/ledger`, or a path the policy lets the file tools read. Thread seals are allowed.
- **What it does:** verifies against the pinned keys, and checks against the configured witness when there is one.
- **Reply:**
  - `{verified, reason?, session, chain_seq, head (12 hex), thread, records, withheld, external_links, witness?}`;
  - then either the newest `limit` records as `{id, key, version, kind, lane, thread, seq}`, or, with `id`, that one record in full with its links (as `symbia_get`).
- **A file that fails verification:** `verified: false` and the reason, and no records.
- Recorded as a `tool_call`.

## 5. Promotion and the ledger

- **The ledger file:** `$SYMBIA_HOME/ledger/ledger.sqlite`, a format 3 file with retention `ledger`, no expiry, and session id `ledger`. Its records are `promotion` records. It is never resumed and never cleaned up, and the session code never treats it as a session.
- **`symbia_promote`** (new tool):
  - **Arguments:** `seal` (a path; default: seal the open session now, reusing an unchanged seal, and promote that) and `confirm` (default false).
  - **Without `confirm`:** a dry run reply `{seal, session, chain_seq, records, thread?, already_promoted, supersedes?}`.
  - **With `confirm`:**
    1. Copy the seal and its sidecar to `ledger/<session>-<seq>[.thread-<tag>].sqlite`.
    2. Write a `promotion` record keyed `promotion.<session>`: `{session, chain_seq, chain_head, file_sha256, public_key, records, withheld, thread?, file}`. When an earlier promotion of the same session exists, the record links to it with `supersedes`.
    3. Seal the ledger (reason `ledger`).
- **Idempotent:** promoting a file whose sha256 is already in the ledger changes nothing and says `already_promoted: true`.
- **Refused:** a file that fails verification, and a `ledger` seal.
- **Index:** it also reads `ledger/`, so promoted seals stay searchable after their originals are pruned or deleted.

## 6. Tests

- **Reasons and pruning:**
  - Checkpoint and exit seals are pruned once a newer full seal of the same session verifies.
  - Explicit, prediction, thread and reason-less seals are kept.
  - Older sidecars without `reason` still verify.
- **Witness:**
  - Lines are written for full, thread and ledger seals, with the folder created.
  - Config refuses a folder inside the data directory.
  - `ok`, `not witnessed` and `behind` outcomes.
  - A mismatch after re-signing a tampered file: the chain hash still verifies against the new sidecar, but the witness catches it.
  - The CLI's `--witness` output and exit codes.
- **`symbia_open`:**
  - A seal in `seals/`, a thread seal, a file outside the allowed paths (refused), and a tampered file (`verified: false`).
  - The record list and a single record by id.
- **Promotion:**
  - The dry run.
  - `confirm` copies, writes the record and seals the ledger.
  - Again is `already_promoted`.
  - A later seal of the same session supersedes.
  - The ledger file is not resumed as a session.
  - The index finds a promoted seal's records after the original is deleted.
- **Stdio end to end:** record, promote with confirm, check the witness file, open the ledger copy, and verify with `--witness`.
