# R6: stdio sessions survive server restarts

Claude desktop restarts the `symbia mcp` server on its own: 3 times on 7 Oct and 7 on 6 Oct, each a deliberate shutdown (config change, app event), each starting the server twice within a second. Every restart opens a new session for every chat on the desktop: seq restarts at 1, the next record lands in a new file, nothing says why, and agents report it as a growing problem. The quick duplicate start also leaves empty session files behind. Read CLAUDE.md, docs/R3.md (cross-session links, seal before drain) and docs/R5-REPORT.md first. Keep every existing test passing. HTTP (`symbia serve`) sessions are out of scope.

## 1. Open the session lazily

`symbia mcp` no longer creates a session file at startup. It opens one (new or resumed, below) on the first tool call that needs the store. A server that starts and exits without a tool call leaves nothing in `sessions/`.

## 2. Resume the previous session

When the stdio server first needs a store:

- Each open session file has a lock beside it, `sessions/<id>.lock`, holding `{pid, started_ms}` and held with an exclusive advisory lock (`flock`) for the life of the process. A lock that can be taken is stale.
- Candidate: the session file with the latest chain `at_ms` whose retention is `session`, which hasn't expired, whose lock is free (or missing), and whose last chain write is within `resume_window_ms` (new config key, default 14,400,000 = 4 h; `0` turns resume off). A session sealed at its head (by seal-on-exit) is still a candidate: the chain continues and the next seal covers the new records.
- If a candidate exists, take its lock and continue it: same session id and file, the chain continues from its head. Write one `observation` record, key `session.resumed`, lane `apocryphal`, body `{previous_pid, previous_started_ms, gap_ms, resumes}` where `resumes` counts resumes of this session so far (count the earlier `session.resumed` records).
- Otherwise create a new session as today, and take its lock.
- Two live processes never share a session: if the newest session's lock is held, the new process creates its own session.

## 3. Tell the agent

- The first tool reply after a session is opened carries one extra field, `notice`, then never again in that process: `"session <id prefix> resumed after a server restart; gap <s> s; seq continues at <n>"`, or `"new session <id prefix>; the previous one (<prefix>) was not resumed: <reason>"` (reasons: in use, outside the resume window, expired, sealed and resume off), or `"new session <id prefix>"` when there was nothing to resume.
- `symbia_status` adds `resumes` (count for this session) and `previous_session` (when a new session was opened while an earlier one existed).

## 4. Clean up

- On startup, delete session files in `sessions/` that have no chain rows and whose lock is free; these are left by the duplicate starts. Never delete a file with rows.
- On exit, release the lock and delete the `.lock` file.

## 5. Tests

Through the binary over stdio, with a temp `SYMBIA_HOME`:

- Write a record, SIGTERM, start again, write a record: the same session id, seq continues, one `session.resumed` record, the reply's `notice` says resumed, and `symbia verify` accepts the latest seal.
- A second process started while the first is alive gets a new session; its notice names the reason "in use".
- Outside the window (set `resume_window_ms` to 1 and wait), and with `resume_window_ms: 0`: a new session with the right reason.
- Start and close stdin with no tool call: `sessions/` holds no new file.
- Empty leftover files are removed at startup; a file with rows is kept.
- The notice appears on the first reply only.
