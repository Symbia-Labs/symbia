# R7: Symbia builds, signs and releases itself

Three jobs still go through Desktop Commander, outside the ledger. `gh`, `git` over HTTPS, `codesign` and `notarytool` need the login keychain, which the exec sandbox denies. Symbia's own test gate calls `sandbox-exec`, which can't nest (exit 71). And `symbia mcp` won't start inside its own sandbox, because policy load fails resolving `~/.ssh`. R7 adds a narrow, logged way to run named programs without the sandbox, and fixes two bugs. Read CLAUDE.md, docs/R3.md, docs/R5.md and docs/R6-REPORT.md first. Keep every existing test passing.

## 1. Config key `exec_unsandboxed`

A list of rules, default empty:

```json
"exec_unsandboxed": [
  {"program": "/opt/homebrew/bin/gh", "args": ["*"]},
  {"program": "/usr/bin/xcrun", "args": ["notarytool", "*"]},
  {"program": "~/.cargo/bin/cargo", "args": ["test", "*"], "cwd": "~/symbia-v2"}
]
```

- `program`: an absolute path (a leading `~` is expanded) to an existing executable file, stored canonicalized. Config load fails on a relative, missing or non-executable path.
- `args`: tokens matched against the command's arguments in order. A token is exact, except a final `"*"`, which matches any remaining arguments, including none. Without a final `"*"` the argument count must match exactly. `args` may be empty, which matches no arguments.
- `cwd` (optional): the call's `cwd` must be this folder or inside it (compare realpaths).

## 2. `symbia_exec` with `unsandboxed: true`

- New optional parameter `unsandboxed` (bool, default false). Without it, nothing changes, even when the command would match a rule.
- With it, the command is split into words with no shell: single quotes are literal; double quotes allow `\"` and `\\` only; backslash outside quotes escapes the next character. Refuse, before running anything, a command with an unquoted `| & ; < > ( ) $` or backtick, a double-quoted `$` or backtick, or an unclosed quote: `refused: unsandboxed commands run without a shell (no pipes, redirects, variables or substitution)`.
- The first word picks the rule. A bare name matches a rule whose program has that file name. A word containing `/` must canonicalize to the rule's program. The first rule whose program, args and cwd all match wins. No match: `refused: no exec_unsandboxed rule matches "<command>"`, followed by the configured rules, one per line.
- The process runs the rule's program by its absolute path, never through `PATH` lookup, with the remaining words as argv, in `cwd`, in its own process group, under the same timeout, yield, job, tail and evidence handling as sandboxed exec. Environment: as for sandboxed exec, except `PATH` is fixed. It is the folders of every rule's program in rule order, then `/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`, with duplicates removed.
- `exec_deny` and the imported Claude `Bash(...)` rules are checked first, as today, and still refuse.
- The file tools are unchanged.
- Logging: the `tool_call` record body carries `sandbox: "none"`, `network: "unrestricted"` and `unsandboxed: {rule: <index>, program: <path>, argv: [...]}`. The reply carries `sandbox: "none"`. `symbia_status` lists the rules as `exec_unsandboxed`. When the list is non-empty, write one line to stderr at startup naming the programs.
- The tool description says plainly: unsandboxed commands are outside the sandbox. A rule for a program that can run arbitrary code (`cargo test`, `git -c`, `gh extension`) grants exactly that. What this buys is a short list and a ledger record, not containment.

## 3. Bug: inline the `symbia_job` action enum

The `action` parameter is declared through `$ref` (`JobAction`), and this client sends the value as a bare word, which fails to parse. Inline it: `{"type": ["string", "null"], "enum": ["status", "wait", "tail", "kill", null]}` or equivalent. No tool's input schema may contain `$ref`.

## 4. Bug: policy load tolerates unreadable deny-list paths

Inside the exec sandbox, resolving `~/.ssh` fails with "Operation not permitted", so `symbia mcp` can't start there. When a deny-list or `exec_unlock` entry can't be resolved because of a permission error, use its lexical spelling as its realpath and carry on. Roots, read roots and `exec_read_allow` still fail on errors other than not-found.

## 5. Tests

- **Config:** a valid rule loads. A relative program, a missing program, a non-executable file and a non-string arg are each refused.
- **Splitting:** quotes and escapes give the right argv. Each forbidden character is refused, both unquoted and inside double quotes. Inside single quotes it is a literal.
- **Matching:** a bare name runs the rule's absolute program even when a different executable with that name comes first in the server's `PATH`. A path word must canonicalize to the rule's program. Args: exact tokens, a final `*`, and a count mismatch. `cwd` inside and outside the rule's folder.
- **Flag:** without `unsandboxed`, a matching command still runs sandboxed. With it, a command no rule matches is refused and the reply lists the rules.
- **macOS, temp home:** an unsandboxed `cat` of a deny-list file succeeds where the sandboxed `cat` is refused. The record and the reply carry `sandbox: "none"` and the rule. `exec_deny` still refuses a matching unsandboxed command.
- **Jobs:** an unsandboxed command that outlives `yield_ms` comes back as a job and can be killed with its group.
- **Schema:** no tool schema contains `$ref`, and `symbia_job`'s `action` lists its four values.
- **Policy load:** with `~/.ssh` a symlink into a folder the test user can't search, load succeeds and `.ssh` stays denied.
