# R13: one layer over every tool

Symbia records the calls made through its own tools and nothing else. Claude Code's built-in Edit, Write and Bash, other MCP servers, and connectors leave no record unless the agent writes one by hand. On October 9 an hour of document edits went through a connector Symbia couldn't see, and none of it reached the ledger until Brian asked. Recording that rests on the agent's conduct slips under a fast cadence. R13 moves it into the tooling, in two parts: a hook for Claude Code first, then a gateway for local MCP servers.

## Part 1: `symbia hook`

Claude Code runs a command on hook events and passes the event as JSON on stdin. `symbia hook` reads one event, writes one record, and exits 0 without printing anything. Every matching hook runs in parallel, and each has a timeout (the default is 600 s; the config sets 5 s for tool events and 15 s for `SessionEnd`).

### Events and records

| Event | Record |
|---|---|
| `SessionStart` | `hook.session` (observation): the client's `session_id`, `cwd`, `permission_mode`, model |
| `UserPromptSubmit` | `chat.prompt` (observation, canonical): the `prompt` field verbatim. This puts every message on the ledger before the agent sees it, which is the rule Brian set and the one that slipped on October 9. |
| `PreToolUse` | `hook.<tool_name>` (tool_call, apocryphal): `tool_use_id`, the input's canonical sha256, the input itself as evidence |
| `PostToolUse` | the same key, next version, linked `revises` to the pre record: the response's sha256 and the response as evidence |
| `PostToolUseFailure` | as `PostToolUse`, with the error |
| `SessionEnd` | `hook.session` again, then a seal of the hook session |

- When a hook fires inside a sub-agent, the input carries `agent_id` and `agent_type`. Both go into the record, and the thread becomes the agent's, linked to the parent thread. That closes the gap from October 6, when a sub-agent's 91 tool calls reached the ledger only through its parent's summary.
- Calls to Symbia's own tools are already recorded, so the hook skips any `tool_name` that names the symbia server (`mcp__symbia__…`).
- Inputs and responses can be large (a `Write` carries the whole file). They go to the evidence folder by sha256, so repeats cost nothing. A payload over 1 MB keeps its sha256 and the first 1 MB, and the record says it was cut.

### Where the records go

The hook is a short-lived process, and the MCP server holds its own session file. Hooks write to a separate session file per Claude Code session, named from the client's `session_id`, with thread `cc:<first 12 of session_id>`. Parallel hooks for the same session queue on a lock held only for the write, instead of refusing as the MCP session lock does. `find` and `report` with `scope: "all"` index these files like any other, and `SessionEnd` seals them.

### Failing loudly

When a hook command exits with anything other than 2, Claude Code goes ahead with the call. So a recording failure is never silent: it goes to stderr. Two modes:

- **observe** (default): a failure to record is reported, and the call goes ahead.
- **strict**: the hook config sets `onFailure: "block"`, so no record means no action. That is axiom 10 made mechanical, at the cost of halting work when the data folder is unwritable.

R13 never refuses a call for any other reason. The veto stays with the rounds that build halt (4) and the array (5); `PreToolUse` is already where they plug in, through exit 2 or `permissionDecision: "deny"`.

### Install

`symbia hook config [--strict]` prints the `hooks` block for `~/.claude/settings.json` or a project's `.claude/settings.json`. Symbia doesn't edit Claude Code's settings itself. The person pastes the block, and the README shows it.

## Part 2: a gateway for local MCP servers

Config gains `upstream`: a list of MCP servers that Symbia starts (stdio) or reaches (streamable HTTP).

```json
{"upstream": [{"name": "midi", "command": "/Users/briangilmore/midi-mcp/target/release/midi-mcp", "args": ["mcp"]}]}
```

- Symbia lists each upstream tool as `<name>__<tool>` (64 characters at most), with the upstream's title, schema and annotations.
- Each call writes `gw.<name>.<tool>` (tool_call): the arguments' sha256 and the arguments as evidence, the reply's sha256 and the reply as evidence, the duration, and any error. Then the reply goes back unchanged.
- Upstreams start on first use, restart once after a crash, and are stopped at shutdown. Their stderr goes to Symbia's log.
- An upstream entry is a permission in itself: Symbia runs the command outside its sandbox, as the person configured it, and records `sandbox: "none"`.
- No secrets in `config.json`. An upstream that needs a credential reads it from its own environment or keychain. A broker (the MCP Wallet idea) is a later round.
- Clients then connect only to Symbia, and the upstream's tools can't be called without a record. This is where the address tree and the array attach later: each gateway call names a target.

First target: midi-mcp.

## Skills

A skill is instructions and scripts that the agent runs with its own tools; it isn't a service Symbia can call. With R13, a skill's script run through Claude Code's Bash is recorded by the hook, and one run through `exec` is recorded by Symbia. Serving Symbia's own skills (start_here first) as MCP prompts belongs to the start_here round.

## What R13 doesn't reach

- Connectors hosted by claude.ai, used from the web or desktop chat (the Docs connector, for example). Those calls go from the client to the service, and the chat apps offer no hook. Only the client could report them.
- Whether a remote connector used inside Claude Code fires the tool hooks is unverified; the first live test checks it.
- Joining the hook session and the MCP server's session into one ledger per conversation needs the client's session id on MCP calls. Claude Code may send it in `_meta`; Claude desktop doesn't.

## Predictions to register at the start of the round

1. A hook write takes under 50 ms at the 95th percentile on Brian's Mac.
2. A Claude Code session with N tool calls outside Symbia yields N pre and N post records, linked in pairs, in one hook session file that verifies after `SessionEnd`.
3. A sub-agent's calls carry its `agent_id` and sit in its own thread.
4. No call to Symbia's own tools is recorded twice.
5. Through the gateway, midi-mcp's tools are listed, each call is recorded with evidence, and the added latency is under 20 ms.

## Tests

- `symbia hook` fed recorded event JSON for each event: the records, the pairing by `tool_use_id`, the sub-agent thread, the skip list, the 1 MB cut, a seal on `SessionEnd`.
- Parallel hook processes on one session: every record lands, and the chain verifies.
- A data folder that can't be written: exit 1 with the reason on stderr.
- Gateway: a fake upstream MCP server in the tests. Listing, a call, an upstream error passed through, and a crash followed by one restart.
