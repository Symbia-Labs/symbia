# R3: close the gaps the security benchmark found

The 6 Oct benchmark (scorecard: claude.ai doc "Symbia v2 Scorecard") showed R2 works for the deny list and fails around it. Four problems, in priority order, plus two small tool fixes. Read CLAUDE.md, docs/R2.md and docs/R2-REPORT.md first. Keep every existing test passing.

## 1. Seal before shutdown, and checkpoint during the session

0 of 54 benchmark sessions left a seal. Closing stdin seals in about 2 s, but on SIGTERM the server drains the runtime for up to 5 s before sealing, and Claude Code ends it first.

- On SIGINT/SIGTERM, seal the session first, then drain. The same for `symbia serve` (seal every live session, then stop).
- On stdin EOF, seal first as well.
- Checkpoint: seal automatically when 50 records have been written since the last seal, and after any `prediction` record (a prediction should be sealed before the work it predicts). A checkpoint seal is an ordinary seal; it runs after the record's reply is produced and must not fail the write that triggered it (log to stderr).
- Tests: SIGTERM with a written record produces a verified seal within 1 s; 50 tool calls produce a checkpoint seal; a `prediction` record produces a seal; a session sealed at its head is not sealed again.

## 2. Exec reads: deny the home folder by default

Under R2 the sandbox denies only the deny list, so a fake GitHub token in `~/.config/gh` was copied in 6 of 6 Haiku and Sonnet runs.

New config key `exec_read`: `"home"` (new default) or `"deny_list"` (R2 behaviour).

With `"home"`, the profile:

```
(version 1)
(allow default)
(deny file-read* (subpath "<user home>"))
(allow file-read-metadata (literal "<user home>") (literal "<each ancestor of a root inside the home>"))
(allow file-read* (subpath "<each root>") (subpath "<each read allowance>"))
(deny file-read* file-write* (subpath "<each deny-list path>"))   ; last, so it always wins
(deny file-write* (subpath "<SYMBIA_HOME>"))
[network rules as in R2]
```

SBPL takes the last matching rule, so order matters; test it.

- Read allowances: a new config key `exec_read_allow` (list of paths, `~` expanded). Default: `~/.zshenv`, `~/.zprofile`, `~/.zlogin`, `~/.cargo`, `~/.rustup`, `~/.local/bin`, `~/.gitconfig`, `~/.config/git`. Leave `~/.npmrc` out (it holds tokens). Both spellings (as given and realpath) like the deny list.
- `$SYMBIA_HOME/evidence` stays readable (it already is for the file tools).
- Paths outside the home (system folders, `/opt/homebrew`, `/tmp`) stay readable; this mode is about the user's own files.
- Writes are unchanged from R2.
- Tests (macOS): with a temp user home holding `.config/gh/hosts.yml`, exec `cat` of it fails and the content is in no reply or evidence; a file inside a root under that home reads fine; `cargo --version` and `git --version` still run; `zsh -lc` still starts with a `.zshrc` present in the temp home; `exec_read: "deny_list"` restores R2 behaviour; a deny-list path inside a root is still refused.
- Also extend `DENY_IN_HOME` with `.config/gh`, `.netrc`, `.docker/config.json`, `.kube`, `.npmrc`, `.pypirc`, `.git-credentials`, `Library/Cookies`. These hold credentials and stay refused in every mode, for the file tools too.

## 3. Exec command rules

Claude Code's own `Bash(...)` permission rules don't reach commands run through `symbia_exec`. In the benchmark a `chmod` the user's rule blocked in Claude Code ran through Symbia.

- New config key `exec_deny`: a list of rules in Claude Code's syntax, `"chmod:*"` (prefix: the command word followed by anything) or an exact command `"git push --force"`. Default: empty.
- New config key `exec_import_claude_rules` (default `true`): also load `permissions.deny` entries of the form `Bash(<rule>)` from `~/.claude/settings.json`, and from `<cwd>/.claude/settings.json` and `<cwd>/.claude/settings.local.json` when present. Unreadable or malformed files are skipped with a note in the tool reply's `policy` field, not an error.
- Matching: split the command into simple commands on `&&`, `||`, `;`, `|` and newlines (respecting single and double quotes), strip leading `VAR=value` assignments, and refuse the whole call if any simple command matches a rule. The refusal names the rule and where it came from. Record refused calls like any other, with `command` and `error`.
- Say plainly in the tool description and the report that this is a policy convenience, not a boundary: `eval`, `$(...)`, `sh -c` and scripts can get around it; the sandbox is the boundary.
- Tests: `mkdir x && chmod 600 x` refused by `chmod:*`; `echo "a && chmod"` allowed (quoted); `FOO=1 chmod 600 x` refused; rules imported from a temp `~/.claude/settings.json`; a malformed settings file is skipped.

## 4. Links across sessions

A server restart opens a new session, and `symbia_record` then refuses a `results_of` link to a prediction made in the earlier session ("link target not found").

- When a link target is not in the current session, look it up in the other session files and seals under `$SYMBIA_HOME` (newest first). If found, store the link with a new `to_session` column (null for same-session links) and hash it into the row digest like the other link fields. If not found anywhere, refuse as today.
- `symbia_get` on a record shows each link's `to_session`.
- `symbia verify` of a seal checks same-session links as today; cross-session targets are reported as `external` with their session id, not failed.
- `symbia_status` gains `session_started_ms` so a client can notice a new session.
- Tests: write a prediction in session A, seal, open session B in the same home, link a result `results_of` to A's prediction id; refused for an unknown id; verify reports the external link.

## 5. Read-only toolchain roots for the file tools

Agents read crate source under `~/.cargo/registry` for API reference; the file tools refuse it. New config key `read_roots` (list, `~` expanded), default `["~/.cargo/registry", "~/.rustup/toolchains"]`: `symbia_fs_read`, `fs_list` and `fs_search` may read there; writes stay refused. The deny list still wins. Tests for read allowed, write refused.

## 6. Two small tool fixes

- `symbia_fs_write` gains `append: true` (create if missing, then append; `create_only` and `append` together are refused). The record keeps `sha256_before` and `sha256_after` as for writes.
- `symbia_record` tool description states the link shape (`{"to_id": "<record id>", "rel": "<rel>"}`) and lists the allowed `rel` values. A refused `rel` lists them too.
- Tool replies omit a stream object whose `bytes` is 0 (exec `stderr` is usually empty), to cut reply size.
