# R4: images, audio, and long-running commands

Three gaps from 6 Oct. Agents can't look at screenshots through Symbia. They can't inspect audio files, which matters for the TASCAM and studio work. And any `symbia_exec` call over about 60 s fails through the Claude desktop link, so long builds are started with nohup and polled from a log outside the evidence store. Read CLAUDE.md, docs/R3.md and docs/R3-REPORT.md first. Keep every existing test passing. Pin exact crate versions and check current versions on crates.io.

## 1. Images in `symbia_fs_read`

Today a binary file is refused with its size and sha256. Image files now come back as MCP image content.

- Detect by magic bytes, not extension: PNG, JPEG, GIF, WebP go out in their own format. TIFF and BMP are converted to PNG. Anything else stays refused as today (HEIC included: say so in the refusal).
- Resize: if the long edge is over 1568 px, scale it to 1568 px (Lanczos3) and send it as PNG for PNG/GIF/BMP/TIFF input, or JPEG quality 85 for JPEG/WebP input. A new optional `full: true` skips the resize up to the hard limit. Hard limit: the encoded image sent is at most 5 MB and 8000 px on either edge. Anything over that is downscaled further, never refused for size.
- The reply is two content blocks: the image, then a short text block with `{path, format, width, height, sent_width, sent_height, bytes, sha256}`.
- The record (`tool_call`) keeps `sha256_before` of the file and adds `image: {format, width, height, sent_width, sent_height, sent_sha256}`. The image as sent goes in the evidence store by its sha256 like exec output, so a seal covers exactly what the model saw.
- The path policy applies as for any read.
- Tests: generate a small PNG, a 4000×3000 JPEG, a GIF, a BMP and a non-image binary in a temp root. Check content types, the resize sizes, `full: true`, evidence written, and the binary still refused.

## 2. Audio in `symbia_fs_read`

As far as we know, Claude can't take audio input, so audio comes back as measurements plus a picture the model can read.

- Decode with `symphonia` (WAV, AIFF, FLAC, MP3, AAC/M4A, Ogg Vorbis). Detect by probing the content, not the extension.
- Text block: `{path, codec, container, sample_rate, channels, bits_per_sample (when known), duration_s, frames, per channel: peak_dbfs, rms_dbfs, dc_offset, clipped_samples (|x| >= 0.999), integrated_lufs and true_peak_dbtp (whole file, via the ebur128 crate), sha256}`. Round dB values to 0.1.
- Image block: one PNG, 1200 px wide. On top, a waveform per channel (min/max per pixel column), with a time axis in seconds. Below, a spectrogram of the channel mix: STFT with window 2048 and hop 512, Hann window, log frequency axis 20 Hz to Nyquist, dB colour scale from −100 to 0 dBFS, axis labels drawn in. Draw labels with a small built-in bitmap font or a pinned font crate; don't load system fonts.
- Optional `start_s` and `end_s` analyse and draw a window of the file, for detail on long recordings. The measurements apply to the window and say so.
- Optional `audio: true` also returns an MCP `audio` content block (base64, original bytes, files up to 10 MB) for clients that accept audio. Without it, no audio bytes are sent.
- Limits: files up to 2 GB are analysed by streaming; don't hold the decoded file in memory. Anything over 30 min without a window draws at reduced resolution and says so.
- Record: `audio: {codec, sample_rate, channels, duration_s, window}`. The PNG goes to evidence by sha256.
- Tests: generate a 1 s 1 kHz sine at −6 dBFS (stereo WAV, 48 kHz, 24-bit) and check peak ≈ −6.0 dBFS, RMS ≈ −9.0 dBFS, 0 clipped samples, duration 1.0 s, and a PNG of the right width. Also a clipped square wave (clip count > 0), a silent file (peak reported as -inf as `null` with a note), a short FLAC if a pure-Rust encoder or a checked-in tiny fixture is available, and a non-audio binary that is still refused.

## 3. Long-running commands

- `symbia_exec` gains `yield_ms` (default 45,000; at most 50,000). If the command is still running when `yield_ms` passes, the call returns at once with `{job: "<id>", running: true, pid, started_ms, stdout/stderr tails so far}`. The command keeps running, with its `timeout_ms` (whose max rises to 3,600,000 for jobs) and the same sandbox, rules, process group and evidence capture. A command that finishes within `yield_ms` replies exactly as today.
- New tool `symbia_job` with `{job, action}`, where `action` is `status` (the default), `wait` with `wait_ms` (at most 50,000), `tail` with `bytes`, or `kill`. Replies give `running`, `exit` (when done), `duration_ms`, stream tails, and evidence paths when finished. Annotations: `title "Check a job"`, readOnlyHint false, destructiveHint true (because of kill), idempotentHint false, openWorldHint false.
- `symbia_exec` gains `tail_bytes` (default 8,192; between 256 and 65,536) to size the stream tails in the reply.
- Records: the start writes the usual `tool_call` with `job` and `running: true`. When the job ends (exit, timeout or kill), a `tool_call`-kind record with key `job.<id>` carries `exit`, `duration_ms`, stdout/stderr sha256 and evidence, linked `revises` to the start record. `symbia_job` calls are recorded like other tools.
- Jobs belong to the server process. On shutdown, kill running jobs' process groups, record them as `killed: "shutdown"`, then seal (seal-before-drain still holds).
- `symbia_status` lists running jobs.
- Tests: `sleep 2; echo done` with `yield_ms: 500` returns a job; `wait` returns exit 0 and "done"; a job past its `timeout_ms` is killed and recorded; `kill` works; `tail_bytes` trims; shutdown with a running job records it as killed and seals; a short command still answers in one call.
