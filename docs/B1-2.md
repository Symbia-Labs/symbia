# B1, part 2: full chain coverage, key pinning, streamable HTTP, session resume

Part 1 is in `docs/B1-REPORT.md`. Read CLAUDE.md, that report and this file. Keep every part 1 test passing unless a test asserts the old chain format, in which case update it.

## 1. The chain covers every write-time field

Today the chain hashes only the record id, so `lane_reason`, links, `expires_ms` and the estimates can change in a live file without breaking the chain.

- Add `format INTEGER NOT NULL` to `file_meta`; new files are format 2.
- `row_digest` = sha256 of the RFC 8785 JSON of `{id, key, version, kind, lane, lane_reason, body, model, session, at_ms, expires_ms, est_host_ms, est_chars, links}`, where `links` is the record's outgoing links sorted by `(to_id, rel)`. Nulls appear as JSON null.
- Chain `hash = sha256(prev_hash || row_digest || at_ms as 8-byte big-endian)`.
- The actual cost fields (`host_ms`, `chars`) stay outside the live chain and are covered by the seal. `verify` requires them to be non-null in a sealed file.
- `verify` recomputes every `row_digest`. Add a tamper test for each newly covered field: `lane_reason`, a link's `rel`, a link's `to_id`, `expires_ms`, `est_host_ms`, `est_chars`.
- Format 1 files from part 1 still verify under the old rule (dispatch on `format`, absent means 1).

## 2. Key pinning

- `keys/trusted.json`: a list of `{public_key, label, added_ms}`. The device's own key is added on first use.
- `symbia verify` trusts only keys in that list by default, and exits 1 with `untrusted key <12 hex>` otherwise. `--trust <hex>` adds one key for that run only.
- `symbia trust add <hex> <label>` and `symbia trust list`.
- Tests: a seal re-signed with a fresh key fails as untrusted; passes with `--trust`.

## 3. Streamable HTTP

- `symbia serve [--listen 127.0.0.1:7341]` serves the same tools over MCP streamable HTTP using rmcp's server transport. Bind to loopback by default and refuse a non-loopback address unless `--allow-remote` is given.
- Each MCP session (its `Mcp-Session-Id`) maps to one session file. Store the MCP session id in `file_meta.mcp_session_id`.
- `symbia mcp` (stdio) keeps working unchanged.
- `symbia_status` adds the session id and `expires_ms`.

## 4. Session resume (prediction S1)

Over streamable HTTP, a client that loses its connection and comes back with the same `Mcp-Session-Id` before the session's expiry continues the same session file, and the chain continues from the same head.

- Test `tests/s1_resume.rs`: start `symbia serve` on a free port, initialize a session, write a record, drop the client's connection, reconnect with the same session id, write a second record. Assert both records are in one file and the second's chain seq follows the first's.
- A restart of the `symbia serve` process is out of scope: write in the report what happens to a client in that case.
